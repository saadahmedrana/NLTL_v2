## Naming rule

Canonical local names use ASCII-only `lowerCamelCase`:

1. Start with the engineering subject or component.
2. Follow with the characteristic.
3. Add a condition or qualifier only when it changes the meaning.
4. Expand opaque symbols and abbreviations where the source defines them.
5. Do not put units in the local name.
6. Preserve every original symbol, abbreviation, and source label as an alias.
7. Reuse an external URI only after exact identifier and semantic verification; lexical similarity alone is not a mapping.

Examples of Stage 2 cleanup include `A_required_cm2` -> `requiredShearArea`, `deadweightTonnes` -> `deadweight`, `sNcurveType` -> `stressLifeCurveType`, and `solely24HourDaylightOperation` -> the Boolean predicate `operatesOnlyInContinuousDaylight`. Units and original notations are stored separately as metadata and lineage.

## Unit and value model

Every engineering quantity uses:

`entity -> canonical property -> qudt:QuantityValue -> qudt:numericValue + qudt:unit`

The schema-only quantity shape requires exactly one decimal numeric value and exactly one unit IRI on each quantity node. Of the 258 quantity properties:

- **255** have a canonical QUDT recommended unit.
- **3** viscosity properties deliberately have no global unit recommendation because the source does not distinguish dynamic from kinematic viscosity. For those three, the manufacturer minimum, observation, and manufacturer maximum must use the same declared viscosity quantity kind and unit within a case.
- **28** distinct asserted QUDT unit IRIs were checked against the official QUDT unit vocabulary.

Scalar states use explicit XSD datatypes. Regulation-defined value sets such as Finnish-Swedish ice class, IACS Polar Class, and IMO polar ship category use IRIs rather than free text.

## Structural patterns

- Core values: canonical property with typed scalar, controlled-value IRI, entity IRI, or QUDT quantity node.
- Time/history: SOSA Observation with feature of interest, observed property, result time, and result.
- Documents/tests/approvals: provenance-bearing evidence nodes; evidence source is structurally required.
- Evidence lifecycle: Draft, Submitted, UnderReview, Approved, Rejected, Expired, or Revoked.
- Compliance state: Compliant, NonCompliant, NotApplicable, or Unknown.

Candidate property shapes are open and contain no global requirement cardinalities. These shapes are structural QA only; requirement-specific cardinalities and logic will be generated by the pipeline.
