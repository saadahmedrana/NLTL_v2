NLTLv2.0 v0.9.2 VS RESULT-PRODUCING MVP — 24 NOVEMBER 2026

Retain useful integrity, context, diagnostics and isolation capabilities;
consolidate their implementation. Current NLTL adds semantic review/retrieval
and targeted repair to an original baseline that performed syntax recovery
only. Its additional machinery has not yet demonstrated reliable end-to-end
live repair. Simplification should address that practical failure without
restoring handwritten regulatory solutions, compliance witnesses or bespoke
repair permissions as production inputs.

DIRECT ARCHITECTURE COMPARISON

MVP baseline: shared scoped context + two examples -> generation -> extraction,
static/Meta-SHACL/runtime checks -> at most three syntax-repair calls -> terminal
candidate/diagnostics -> separate evaluation. Non-syntax findings are terminal,
not repair feedback. No semantic acceptance is claimed.

v0.9.2: source documents + ontology/representation + common research scope,
no examples -> generation -> generic checks/execution probe -> bounded evidence
retrieval/source-grounded review -> targeted repair and recheck -> accepted
candidate or NO_VERDICT -> separate evaluation. Single-shot still closes after
one generation. Explicit current uncertainty and immutable state are useful;
repeated context and brittle citation/path conventions need simplification.

SMALLEST COHERENT END-TO-END PIPELINE

1. Build/freeze one source/schema/scope/settings bundle; verify hashes and render
   the common initial request. No regulatory answer profiles or fixture IDs.
2. Generate once per arm, saving raw output and complete candidate/hash.
   Single-shot closes here; later diagnostics cannot improve its response.
3. NLTL runs one check stage: Turtle + Meta-SHACL, canonical/type/unit/path,
   shape-aware SPARQL/pre-binding, activation and execution-only probe. Preserve
   original diagnostics; distinguish code defects from uncertainty/infrastructure.
4. One bounded controller manages grounded review, evidence retrieval and repair.
   Supply full current code once, previous code for change review, one evidence
   catalog, findings/probe and unresolved issues. Re-review unchanged code when
   evidence changes; validated code findings can trigger full-latest-candidate
   repair, followed by step 3. Format retries keep original state. Use one
   combined change/removal assessment and one event/finding ledger.
5. Accept only after checks and complete grounded review; otherwise explicit
   bounded NO_VERDICT. Freeze selection/close dispatch, then independently evaluate
   in a separate process. Never return labels/counterparts/reference solutions
   to the controller. No selection by external score.

Implementation can consolidate to context/resolver, checker, review validator,
controller and transport over shared records; evaluation remains separate.
Preserve these capabilities and trust boundaries, not every existing module.
