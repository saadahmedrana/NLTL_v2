# v0.7.0 protocol, context and verification scope

Schema context uses genuine ontology and JSON-LD declarations, not compliance answers. Relevant range classes and named instances are traversed generically. Ancestors are evidence; broad ancestor classes are not exclusive owners or reasons to pull every ontology term into context. Exact original schema files/hashes remain unchanged. A known serialization error `qudt:value` receives the unique declared numeric-predicate replacement, location, original diagnostic and JSON-LD evidence; this never authorizes deleting numeric/unit/query constraints or numeric conversion.

Aliases are limited to `exact_source_excerpt→source_excerpt`, `exact_candidate_excerpt→candidate_excerpt`, `exact_previous_excerpt→previous_excerpt`, `exact_evidence_excerpt→evidence_excerpt`. Equal canonical/alias values normalize with an audit event. Conflicting aliases or duplicate JSON values reject. No quotation text, whitespace, claim or decision is rewritten. Raw responses and normalized objects are stored separately. Error packets identify exact JSON path, code, category, observed content and expected structure. Malformed structure, truncation, invalid source/candidate quotations and unsupported schema assertions are distinct from a valid UNRESOLVED interpretation.

`unchecked` entries are `{scope, material, reason}`. Legacy strings are conservatively material. A material entry produces a blocking UNRESOLVED_CONTEXT finding even if the reviewer says ACCEPT; it is not retried as malformed JSON. A shape with no supported activation, no active reachable constraints or deactivated reachable enforcement is blocked without inventing the correct target. Core targetClass/targetNode/targetSubjectsOf/targetObjectsOf and explicit implicit-class targets are supported; custom targets remain unresolved. Nested shapes can be untargeted. Empty-target probes exercise activation/execution only, deliberately ignoring conformance and supplying no regulatory expected outcomes.

Change manifests retain exact code diff, versions/hashes and grouped removed functional triples. Every removal alert needs a `removal_assessments` entry with a source quotation, previous/current excerpts, specific explanation and supported-removal/replacement/regression/unresolved disposition. This is model review, not an independent correctness certificate. Removal can be justified (for example an excessive old restriction), but disappearance alone is not resolution.

Source selection retains exact anchored clause sections, numbered parent text, scope/definition sections and recursively referenced local provisions. Ambiguous references are retained/flagged; external references are never silently mapped to a same-number local section. Missing or repeated anchors and explicit supporting files fall back to complete text. Full files remain source-accessible by verified span retrieval. Selection does not prove all implicit references/definitions have been found. A complete sidecar includes omitted sections, offsets and hashes; prompts contain compact selection metadata instead of repeating the index. Unsupported or material uncertainty must stop acceptance.

Prompt accounting reports exact rendered bytes/characters and separates source, schema, code, diagnostics and JSON/system overhead. It does not claim offline byte counts are provider tokens. Historical-size comparisons replace only source/schema context, while complete software-test packets include the actual new schema/retry/removal protocol. Full raw responses stay in artifacts rather than duplicating previous raw code in every repair request.

Azure Responses documentation: https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/structured-outputs and https://learn.microsoft.com/en-us/rest/api/microsoft-foundry/azureopenai/responses . The documented field is `text.format` with `type=json_schema`. Optional strict schema dispatch is implemented and tested by local serialization only. Aalto gateway/model support is unverified (public Aalto service page was inaccessible during this offline implementation); default configs therefore use bounded_json. Do not infer gateway capability from upstream Azure documentation. No online capability probes, credential reads or model calls occurred. A future verified capability sets `provider_capabilities.responses_text_json_schema=true` with supporting documentation and `review_output_mode=json_schema`; this does not bypass evidence checks or trigger fallback calls.

Both historical runs/scores are immutable. Retrospective saved-response/candidate replay is software diagnostics only. Independent evaluation fixtures, labels and counterparts remain denied to production.
